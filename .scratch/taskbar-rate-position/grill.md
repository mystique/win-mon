# 任务栏速率位置：自动设计讨论

## 输入与边界

用户要求：Rate Strip 可在任务栏左侧或右侧显示；默认右侧；右侧箭头在速率右边，左侧箭头在速率左边；单位与箭头保持固定距离，数字变化不导致整体移动；按活动字体自动预留空间；新增一级菜单及 Left / Right 两个选项，持久化选择。“一位小鼠”按上下文解释为一位小数。

## 仓库证据

- RateStrip 的 MeasureSize 按 `999.9 G/s ↑/↓` 测量，Render 把完整速率和箭头拼起来右对齐；PlaceBesideNotificationArea 锚定 TrayNotifyWnd 左侧，每秒刷新。
- WinMonCore::FormatRate 使用十进制 K/s、M/s、G/s，保留一位小数。现有测试明确要求 999999999 bytes/s 输出 `1000.0 M/s`；G/s 是最高单位，无数值上限。因此 999.9 并非现有输出的严格上限。
- Operator Menu 已支持递归子菜单、radio 项和选择 token；OperatorSettingChange 已有实时应用、持久化、失败回滚机制。
- Settings 使用 HKCU\Software\Win Mon；Rate Font 可选 6–12 pt。CMake 已承载核心、字体、浮动显示测试；Windows smoke 覆盖真实桌面场景。
- ADR-0001 目前限定 notification-side locus，左侧选项扩展此约束；ADR-0002 的 primary bottom taskbar 限制仍保留；ADR-0007 的注册表设置策略沿用。

## 设计树

位置语义 → 左侧几何 / Shell Recovery / 空间不足；固定布局 → 字体测量 / 单位切换 / 数值溢出；菜单 → 当前选择 / 应用失败 / 持久化；测试 → 既有测试入口 / 原生桌面验证。

## Round 1：无前置依赖的选择

1. Q：左侧指任务栏左端还是仅把文字左对齐？推荐：主屏底部任务栏左端区域，距左边缘 4 DIP；右侧保留通知区左邻位置。理由：用户明确要求显示位置变化。自动选择假设：左侧从左边缘开始，不解释为开始按钮之后。
2. Q：如何命名和摆放菜单？推荐：英文一级 `Speed Text Position`，置于 Network to Monitor 后、现有分隔符前；子项 `Left`、`Right`，单选圆点。理由：符合英文 UI 和现有菜单模型。自动选择假设：文案与插入位置。
3. Q：单位和采样是否改变？推荐：保持现有十进制三种单位、一位小数、每秒采样，浮动显示不受位置设置影响。理由：缩小影响面，不擅自修改已被测试固定的格式规则。
4. Q：采用什么持久化？推荐：新增 `SpeedTextPosition` DWORD，0=Right、1=Left；缺失、类型错误、未知值、读取失败均回退 Right。理由：遵循现有用户级设置。自动选择假设：键名和编码。

## Round 2：依赖位置、格式和菜单的选择

5. Q：如何防止左右布局抖动？推荐：拆分固定箭头栏、固定数字栏、固定单位栏；两行共用栏位。Left 为箭头、数字、单位；Right 为数字、单位、箭头。数字始终右对齐，单位栏左边界固定，箭头独立固定；数字变化只能改变数字左端。理由：单纯拼接字符串无法保证比例字体下单位和箭头间距固定。
6. Q：预留 999.9 是否足够？推荐：正常容量包含四位整数加一位小数（包括 1000.0），数字栏以实际字体最宽数字的五个数字位置、小数点及必要字距保守测量；单位栏取 K/s、M/s、G/s 最大实际宽度，箭头栏取 ↑/↓ 最大实际宽度。理由：保留已有边界输出，且比例字体中 9 未必最宽。自动选择假设：容量扩大一位，避免改变共享格式化。
7. Q：超出固定数字栏怎么办？推荐：只在数字栏显示明确的省略号 `…`，保留完整单位和方向，不扩窗、不伪造封顶数值、不截断半个数字。理由：G/s 无上限，有限窗口不能承诺无限数字；异常时明确表达无法容纳。自动选择假设：超宽显示策略。
8. Q：间距、字体和 DPI 怎么处理？推荐：沿用现有 4 DIP 外侧定位间距，栏间距按活动字体空格宽度且至少 1 DIP；字体、样式、字号、DPI 或窗口重建时重新测量。单位栏左边界与箭头栏的相对位置固定；换字体后可重新布局。理由：固定的是当前布局内的位置，不是跨字体的像素尺寸。
9. Q：左侧与系统控件冲突怎么处理？推荐：不修改系统任务栏子窗口；只有能验证左端完整区域空闲时显示，否则暂时隐藏并继续重试，保持 Left 选择，不静默改到 Right。理由：左端可能有 Widgets、Start 或其他控件，不能承诺始终有空白。未知：本机 Windows 11 各版本可观测的占用几何尚未验证；以不能证明空闲就隐藏作为保守规划假设。
10. Q：选择如何应用并失败恢复？推荐：复用现有设置事务，即时改变位置和绘制顺序，成功后写注册表；失败回滚并沿用已有错误反馈。任务栏不可用时允许保存目标选择，待恢复应用；空间不足属于暂时不可见，不属于设置失败。同项重复选择不写入。理由：持久化与菜单状态保持一致。

## Round 3：恢复、文档和验收

11. Q：运行时需要覆盖哪些重建场景？推荐：启动、Explorer 重启、主屏/DPI 切换、字体更换、主题和任务栏几何变化均使用同一目标位置及测量规则；任务栏不可用时保留采样、托盘和浮动显示。理由：与 Shell Recovery 既有契约一致。
12. Q：测试采用什么边界？推荐：复用核心菜单/设置事务测试；优先从 RateStrip 对外输入到实际布局/渲染结果的原生测试验证固定锚点，仅在不可观察时增加最小布局测量入口；注册表恢复和真实任务栏遮挡通过 Windows smoke/人工验收。理由：测试用户可见结果，避免为每个私有函数创建接口。该推荐自动接受。
13. Q：需要新 ADR 吗？推荐：不新增 ADR，易逆转的布局无需新架构记录；在 ADR-0001/0007 添加明确标为 proposed 的范围扩展，与当前实现区分。CONTEXT 新增精简的拟议位置术语。理由：不能把文档阶段当成已实现功能。
14. Q：讨论是否完成？推荐：完成。所有分支已有选择；左端占用检测为显式证据未知，并有保守行为与实现验证门槛。最终共享理解确认仅为文档综合自动满足。
