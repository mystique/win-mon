# Taskbar Speed Text Position validation

Date: 2026-10-11
Implementation: complete
Acceptance: current desktop passed; broader manual Windows scenarios pending in ticket 03

## Environment

Windows reported by CMake: 10.0.26300; Windows SDK 10.0.26100.0; Visual Studio 18 2026 / MSVC; x64 Release. Current primary bottom taskbar: 3840 px wide, 72 px high, 144 DPI, centered taskbar controls; the left end has usable free space. No changes to user taskbar preferences or physical monitor configuration were made.

## Automated results

- CMake x64 configuration and Release build succeeded; eight CTest executables passed.
- RateStripLayoutTests: 36 font/style/size/DPI combinations (Segoe UI, Arial, Consolas; normal and bold italic; 6/12 pt; 96/144/192 DPI), both sides, K/M/G units, both rows/arrows, 0.0/9.9/999.9/1000.0/oversized numeric values. Stable unit/arrow pixels and complete row output match an unclipped reference with a literal expected ellipsis for overflow. Negative glyph bearings are measured, not assumed from text metrics alone.
- RateStripWindowTests: actual Left shown (visible Left verified=1), 4 DIP taskbar anchor, continuous refresh, temporary native occupied-region hiding and return, actual XAML Start button corner-padding rejection, unknown-host rejection, live position transaction rollback on persistence failure, Left/Right recreation retention and font relayout. Three Left refreshes took approximately 38–42 ms in measured runs. These timings are observations, not a universal latency guarantee.
- SettingsTests redirects HKCU only inside its process to an isolated temporary key. It verifies default Right, stored Left/Right, unknown DWORD values, wrong type and malformed DWORD size, then removes its own key. It does not touch real operator preferences.
- Existing core menu/transaction, rate font, network observation, floating renderer and floating window tests passed.
- Windows smoke used the CMake-built application, opened its actual menu through Rate Strip right-click, navigated Network → Position → Left using targeted native menu key messages, and verified the saved Left value. Restart fixtures verified missing/wrong-type/unknown/Right/Left settings, including two visible Left application starts. TaskbarCreated broadcasts exercised the host recovery route.
- Smoke now rejects zero HWND results and treats null/empty optional native-window filters consistently. The old helper could return a false success before finding a window; this was corrected before the final successful run. Startup waits for GUI initialization and allows the normal sample retry if a shell provider times out at launch.
- Smoke snapshots/restores registry values and original value kinds in finally, and terminates only test-owned processes. The operator's previously running executable was restored after testing.

## Review

Independent Standards and Spec reviews initially found that composite interactive controls were treated as empty containers and that rendering checks did not prove complete glyph output. Occupancy now ignores only the verified structural XAML frame and checks every other control's full bounds. Stronger rendering comparisons caught italic clipping and drove the negative-bearing fix. Both re-reviews reported no remaining confirmed defect; manual acceptance limits below remain.

## Pending manual scenarios

- Real Widgets on/off and centered/left-aligned taskbar preferences, search/Start open states, and crowded application icons. The synthetic obstacle and real Start-padding check verify the collision mechanism, not every preference combination.
- Real Explorer process restart rather than a TaskbarCreated broadcast.
- Physical primary-monitor reassignment and live monitor DPI changes rather than offscreen DPI measurement and native window recreation.
- Actual light/dark preference switching and notification-area expansion/contraction while running.
- Taskbar removal and unsupported edge alignment in a real shell configuration, plus all menu entry points in each hidden/visible state.
- Other Windows 11 shell builds and unusual fallback/font families outside the tested set. Unknown shell trees/space remain hidden and retried; a permanently hidden Left on an unsupported tree is not evidence of usable Left support.

These limits remain unchecked in ticket 03. Implementation completion is separate from full desktop acceptance.
